# MR Memory 开发与实验记录

本文只记录可复核事实、实验配置和成本。真实群聊正文及数据库快照位于 Git 忽略的
`.dev/`，不得提交。插件 ledger 也只保存查询/结果哈希、工具参数、证据 key 和 token，
不保存模型隐藏推理。

## 2026-08-17：恢复可测弱基线 / 0.17.1

0.17.0 把回答前的语义终判移到宿主本地规则，但没有先用同一批真实遮罩调用证明其语义损失
可接受。这违反了本项目“embedding 只生成候选、LLM 负责运行时语义 gate”的核心假设，
也把延迟优化错误地提前成了架构结论。0.17.1 因而恢复 0.16 的可测结构基线：宿主先预取
最多 8 个 Episode、80 条原始消息和 60k 字符证据，独立 Provider 开完整思考做一次
`brief / none / escalate` 判断；只有 `escalate` 才进入最多 6 步的私有图工具循环。

这次恢复不把 0.16 宣称为合格语义方案。其 prompt 明确把 `escalate` 规定为例外，是否因此
过早停止、丢失群内梗义、多跳关系和主体消歧，必须由真实调用遮罩回放、人工证据标注和盲评
决定。0.17 的本地 materializer 保留为离线消融 arm，不再参与线上 `every_request` 终判。
精确公开 brief/source trace、历史调用子图、反馈前向图物化和热重载 inflight drain 均保留。

## 2026-08-17：本地工作记忆、反馈前向通路与调用子图 / 0.17.0

线上账本显示，旧回答前重建即使最终返回“没有相关记忆”，仍会把本地候选与原始证据再次交给
独立 Provider 做一次完整语义判断；有用调用的中位时延约 21 秒，p95 约 80 秒。该结构把
已经由后台模型构建的记忆在每次 `/chat` 上重新表述一遍，既重复花费 Token，也把外部网络
时延串行加到主回答前。0.17.0 将普通路径改为 materialized working memory：本地 embedding
只负责排候选，SQLite 展开真实证据，宿主按已存的 `epistemic_status` / `epistemic_state`
保留结论、冲突和疑虑，再把有源键的有界 JSON 交给 AstrBot 主 LLM 做最终相关性判断。
没有固定相似度阈值被提升为语义判决；独立潜意识模型仍负责后台整理、反馈学习和手动深挖。

旧反馈维护允许 `graph_mutations=[]`。实测 166 条决策中没有一次显式前向图修改，因而行为
假设虽能提交，plastic layer 仍高度碎片化。现在模型仍先决定归因、scope、cue、陈述、未来
行为和置信度；若一条已提交的 `upsert` 没有携带图修改，宿主才把这些模型字段物化为一条
有原始消息证据、可审计且可继续强化/抑制的 `guides_response` 通路。该兜底不处理 ignore、
不跨群、不改账户主体，也不能引用本次证据包之外的消息。

运行账本过去只保存简报哈希，控制台因此无法回答“这次究竟给主模型看了什么”。新调用会
保存公开记忆简报、简报实际引用的 source keys、访问过的候选证据、interaction trace 以及
反馈产生的 hypothesis / mutation ID。最近调用的每一行都可打开专用子图；旧调用仍可由
reconstruction step 还原访问证据，但界面会明确提示无法恢复当时未落盘的最终简报，避免用
当前图伪装历史结果。隐藏推理仍不保存。

首次部署 0.17.0 时，热重载恰好撞上一条刚开始的手动深挖调用。旧实例的 `terminate()`
立即关闭各群 SQLite，仍在运行的 tool loop 随后虽然读到了证据，但 trace/usage 落盘连续报
`Cannot operate on a closed database`，深挖工具最终向主模型返回失败；主模型继续走联网路径并
完成回复。修复后实例分别跟踪主交互任务和重建任务，`terminate()` 会先等待这些请求自然
完成，再取消维护 worker、关闭数据库并释放 embedding。该等待只影响插件热重载，不改变
正常消息链，也不通过取消用户调用换取快速卸载。

## 2026-08-09：实时状态、响应协议与反馈队列修复 / 0.16.3

线上 0.16.2 的运行面板把 `finish_experiment()` 写入的规范终态 `COMPLETED` 按小写
`completed` 比较，因而将成功调用全部显示为失败；时延又只累计 Provider usage 事件，超时
且没有 usage 的调用会被记成 0 ms。0.16.3 统一按大小写无关的终态统计，单列 `RUNNING`，
并以实验开始至结束的墙钟时延和 LLM 累计时延中的较大值作为端到端观测值。原始 LLM 时延
仍保留在最近调用明细中，便于区分模型等待和宿主处理时间。

同一轮检查发现一个反馈批任务处于早期版本遗留的 `COMPLETED` 状态；维护队列的合法终态
实际是 `DONE`，所以它既不能被 worker 领取，也不会在新的 proposal 到来时由唯一键冲突
重新打开。schema v15 在每个群库首次打开时把该遗留值迁移为 `DONE`，enqueue 仍兼容
`COMPLETED`，公开完成接口也把该别名规范化为 `DONE`。插件恢复阶段随后会依据真实的
`PENDING` proposal 重新建立一个可领取的批任务。

Provider 偶发把完整 JSON 留在 reasoning 末尾、在 completion 前后附带文字，或生成结构
不合格的 final。新解析器只接受 public completion 或 reasoning 末尾的完整顶层对象，并继续
执行原有证据 key、候选 ID 和 schema 校验；不会把 reasoning 中间的草稿对象当作结论。
主调用仍使用完整思考和原输出上限。只有严格校验失败时才额外进行一次关闭思考的协议修复，
该调用只负责把上一轮结论重新序列化，并单独写入 token ledger。

可塑图的关系键由宿主持有。普通 `upsert_edge` 再次提出同一稳定键但只改变名称或描述时，
现在复用当前 ACTIVE 定义并记录 `relation_definition_reused`，避免一次措辞漂移丢弃整条
证据；真正修改关系 schema 仍必须显式调用 `revise_relation`，节点类型也继续按 ACTIVE
schema 校验。

部署复验进一步暴露了反馈包形状错误：运行时发送的是 `proposal.id`，证据 allowlist 却只读
顶层 `proposal_id`。模型完成归因后，宿主因此以“没有可归因证据”中止。修复后遗留任务被
显式重开，两个真实 proposal 分别提交为 `ACTIVE` 与 `PROVISIONAL`；热重载期间取消的 worker
也会立即归还 lease 且不消耗一次重试，避免留下最长一小时的假 `RUNNING`。

这次成功运行同时给出了两段式路径的真实成本：2 条 proposal 墙钟 260 秒；归因和学习两次
LLM 调用分别为 59.7 秒 / 12,443 token 与 58.9 秒 / 10,325 token，剩余约 141 秒主要来自
提交前对每条候选串行执行 Harrier 关联检索。0.16.3 因而回到一次完整语义决策：同一调用
同时输出 ignore 或最小学习计划，既有行为假设由本地 SQL 提供，已激活可塑边随 trace 提供，
不再在关键路径重复做向量去重。最终 trace、账号、群、证据键、负向边和修改范围仍由宿主
确定性校验；这里删除的是重复计算，不是用固定阈值代替 LLM。

## 2026-08-07：查询式记忆图与复杂网络分析 / 0.16.0

旧控制台先按节点类型把最多 200 个节点排成九列，再把高达上万像素的虚拟画布缩回一屏；
真实大群因此只剩一条无法阅读的竖线。更重要的是，后端先截断节点再交给浏览器，既无法保证
搜索命中历史条目，也会把目标节点真实存在的邻接边截掉。该页面只能证明“存有一些节点”，
不能回答某条记忆与什么相连。

0.16.0 改为查询优先：后端在当前群的完整可分析结构上搜索条目，按目标返回 1–3 跳邻域；
任意两个节点可以计算最短路径。选中节点会列出画布内每条入边、出边、关系类型与相邻条目，
并可直接把相邻条目设为新的中心。全局图退居结构概览，局部邻域使用同心径向布局，路径使用
线性布局，全局概览使用确定性力导向布局；节点大小编码度，标签只保留中心与枢纽。

分析口径基于当前筛选图的无向投影，提供节点/原始有向关系数、平均度、密度、弱连通分量、
最大分量占比、孤立点、平均聚类系数、关系互惠率、k-core、度分布，以及从最多 24 个确定性
起点估算的平均最短路径和直径。筛选在服务端执行，支持节点类型、群内语义可信状态、关系
类型、最小度、最小 k-core、仅有连接节点和最大连通分量；响应同时区分筛选全集指标与画布
抽样指标，避免把显示上限误称为完整网络。

本轮没有数据库 schema 变更，也不触碰记忆生成、反馈学习、额度或后台维护调度。

### 0.16.1 线上验收与并发修复

最大群线上结构为 9,488 个分析节点、10,380 条有向关系、420 个弱连通分量，最大分量占
66.5%，平均度 2.19，最大 k-core 为 3。查询“好女孩”命中检索线索、情节与主题等候选，
默认两跳邻域返回 35 个节点、38 条关系；中心线索的 9 条直接关系均能从检查器跳转到相邻
条目。隔离进程中的完整查询耗时约 1.09 秒，其中两次复杂网络计算合计约 0.41 秒。

首次在线请求曾出现 19–35 秒延迟，并伴随 33.5 秒事件循环滞后。性能剖析确认图算法本身
不是瓶颈：实时 embedding 检索对 8,239 个向量逐个执行可见性 SQL，反复争用同一个 SQLite
连接锁；主事件循环又在每条群消息到来时同步读取 scope identity，因此被锁竞争拖住。
0.16.1 将 embedding 可见性改为每类一次批量查询，并把已经由数据库绑定验证过的群 scope
缓存到内存。图查询仍在线程池运行；消息捕获不再为了重复身份检查等待数据库锁。部署后的
同库隔离复验中，8,239 向量检索为 0.453 秒，图查询为 1.112 秒；两者并发完成为 1.535 秒，
未再出现旧版逐条 SQL 导致的几十秒锁占用。

验收还修正两处交互语义：查看相邻节点不再清空已选的最短路径起点；局部邻域只有真实超过
画布上限时才标记“已截断”。模型偶发返回空 final completion 时，重建、反馈归因和反馈
合成各允许一次有独立 ledger 记录的重试，避免把一次瞬态空响应直接固化成失败任务。

并发压测最初用第二个 `MemoryStorage` 句柄打开线上库，暴露了另一项恢复语义缺陷：旧迁移
逻辑会把所有 `RUNNING` maintenance job 无条件改回 `PENDING`，即使主进程持有的 lease 仍
有效。该次被影响的 feedback job 已完成全部 proposal，但终态写回失败；确认当前群不存在
任何待处理 proposal 后，将孤立 job 收敛为 `COMPLETED`。代码现只回收 lease 已过期或没有
lease 的任务，并新增“有效 lease 在观察者重开后仍保持 RUNNING”的回归测试。

## 2026-08-06：实时链路收敛、运行控制台与线上复验 / 0.15.1

0.15.0 将回答前自动回忆从开放式工具循环改为一次完整语义判断：宿主先在当前群内预取并
校验有界证据包，独立模型只需返回记忆摘要、无相关记忆或明确升级到深度遍历。手动咨询仍
保留完整遍历。反馈维护先把 15 秒内最多 6 条 proposal 合并，但线上首批复验表明，单次
“全证据 + 判断 + 学习”虽然显著降低 Token，真实延迟仍在 50–101 秒。

0.15.1 因此把反馈拆为严格的两段式协议：第一段只做语义归因，普通后续消息直接结束；只有
确实在评价目标回答的消息才进入第二段学习。第二段才检索现有可塑图关联，产生有证据约束的
行为假设、效用反馈与图修改。两段都使用配置中的独立模型并保留完整推理；embedding 只生成
候选，不参与最终裁决。每一段分别写入反馈额度账本，控制台显示实际路径为“先判断，必要时
学习”。

在生产数据库的只读副本上，用线上同一 DeepSeek V4 Flash Provider 重放两条真实反馈和一条
明显无关的负对照；不修改线上图，不记录正文或隐藏推理。Provider 返回的实测如下：

| 路径 / 样本 | 归因阶段 | 学习阶段 | 输入 Token | 输出 Token | 总 Token | 串行总延迟 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 旧深度反馈基线 | — | — | 未分段 | 未分段 | 104,648 | 178.5 s |
| 0.15.0 线上单段批次 A | — | 101.0 s | 24,211 | 10,485 | 34,696 | 101.0 s |
| 0.15.0 线上单段批次 B | — | 50.3 s | 29,604 | 4,751 | 34,355 | 50.3 s |
| 0.15.1 明显无关负对照 | 4.5 s | 未调用 | 3,358 | 399 | 3,757 | 4.5 s |
| 0.15.1 真实反馈 A | 35.3 s | 42.6 s | 7,381 | 7,198 | 14,579 | 78.0 s |
| 0.15.1 真实反馈 B | 37.4 s | 45.7 s | 5,321 | 7,675 | 12,996 | 83.1 s |

结论不能写成“全面达到 20 秒”：明显无关消息已在 5 秒内结束，且真实反馈 Token 降到旧
基线的约 12%–14%；但两次完整推理串行时，真实反馈仍需 78–83 秒。继续压到 20 秒需要
更换更低延迟 Provider、降低推理强度，或让两个有重复判断能力的阶段投机并行。当前版本不
偷偷关闭思考、不设置 4k/8k 输出上限，也不以固定相似度阈值代替 LLM 的语义裁决。反馈任务
在独立后台 worker 中运行，长推理不会阻塞主聊天回复。

线上排查同时发现一个与模型速度无关的调度错误：旧热加载实例只要存在任意 LIVE 待整理
消息，就会在每批完成后继续调度，导致 1–2 条新目标反复携带 12 条 overlap；插件热重载时
还会把任意非零 LIVE backlog 当成恢复任务。0.15.1 只在 LIVE 待处理数达到配置阈值时继续
调度，启动时只恢复真实持久化任务；每日 sweeper 仍会整理不足阈值的少量消息。线上阈值为
150 条、最长等待为 1440 分钟。修复热重载后没有再出现整理循环，当前仅 2 条 LIVE 待处理，
且没有 `PENDING`、`RUNNING`、`BUDGET_WAIT` 或 `FAILED` 维护任务。

控制台的信息架构改为“运行 / 记忆图 / 账户与别名 / 原始证据”。首屏先回答是否工作、一次
调用多久和多少 Token、产生了什么、有什么在等待；群范围、实际模型、Embedding、整理触发、
反馈窗口和两套额度均直接显示。内部 UMO、哈希和底层参数收进技术详情；当前群的在线额度与
反馈额度可分别重置，重置只移动计费水位，不删除原始 ledger。0.15.1 上线后四个物理群库的
两套额度已再次重置，复验时生效使用量均为 0。

|---|---|---:|---:|---:|---:|---:|---|
| r1 | 原始 LLM 自主停止 | 4 | 12 | 23,566 | 1,094 | 1,868 | 首步已拿到证据却继续浏览，最终错误返回 `NO_RELEVANT_MEMORY` |
| r2 | 加强直接证据停止提示 | 4 | 未完成 | 19,476 | — | — | 模型生成缺少必填参数的 tool call，执行器失败；保留为失败样本 |
| r3 | 无效参数可恢复 + 提示停止 | 6 | 15 | 37,316 | 1,105 | 2,121 | 找回真实证据并改善回答，但过度探索更严重 |
| r4 | r3 + 宿主直接证据门控 | 2 | 4 tools + 1 gate | 5,480 | 1,094 | 1,779 | 找回原话，明确“抢首发”无证据，严格无泄漏 |

共同的一次性构建成本：28,532 uncached input + 4,608 cached input + 20,030 output
= 53,170 token。r4 每次查询路径的受控新增成本为 5,480 重建 + 1,779 MR 主回答
= 7,259 token；这只是本样本的成本，不可直接外推平均线上费用。

r4 相比 r3 将重建 token 从 37,316 降至 5,480，下降 85.31%。门控条件为：

- 工具返回的是初始高分 episode 的原始 `query_event_context`；
- candidate score 至少 0.48；
- 查询与证据存在显著词项交集；
- 原始记录包含 source key。

门控只决定“停止浏览并进入综合”，不替模型判定命题真假。r4 最晚使用的证据时间为
`1785260988`，严格小于 cutoff `1785400304`。

### A/B 结论

Control 只能从最近上下文判断该成员当天一边吐槽一边继续玩，无法确认此前的类魂表态。
MR arm 能准确补充较早的厌倦表态和相关上下文，同时指出未检索到“抢首发/预购”的证据。
因此本例的改进不是单纯让答案更肯定，而是同时提高了 recall 和 calibration。

一个样本只能证明数据流和反事实实验方法可行，不能证明总体效果。后续必须抽取更多真实
调用，以盲评方式分别标注证据召回、事实一致性、遗漏、无根据推断和回答帮助度。

## 2026-08-05：后续反馈闭环真实历史 A/B

### 实现对象

0.8.0 为每次主请求持久化不含隐藏思维链的可观察工作图：request、已激活假设、主 Agent
工具名与参数键/哈希、工具结果哈希、可见 response 和发送组件类型。后续消息进入反馈
proposal，由独立 `deepseek/deepseek-v4-flash` 维护 Agent 检查有界上下文，再由宿主校验
proposal 绑定、严格时间顺序、群/发送者 scope、修改阈值和激活模式，最后在一个 SQLite
事务中写入 Feedback--Hypothesis 边。

负反馈只对实际激活路径做 signed utility credit，不修改事实置信度。前瞻假设分为：

- `always`：跨话题表达偏好，trigger 必须为空，直接走本地快门；
- `semantic`：任务条件规则，必须有 trigger；字面未命中时交给私有潜意识 Agent 在有界
  候选内判断语义改写。

完整不变量见 [反馈图闭环](FEEDBACK_LOOP.md)。

### 样本与遮罩协议

从本地只读真实群聊快照选取两条明确的人类纠正及其更晚真实调用：

1. `no_followup`：用户要求不要再用“你要是想”征询是否继续，而应直接给后续内容；
2. `forced_choice`：用户否定端水回答，要求二选一时只能选一个。

公开记录不写 UMO、数字 ID、昵称或完整上下文。每个 target 只包含其 cutoff 前最近 12 条
消息；feedback 本身也必须严格早于 target。control 与 memory 使用相同的历史 persona、
最近上下文和当前线上默认主模型 `openai/gemini-3.5-flash`，每个 arm 运行 3 次并交替顺序。
维护/激活只执行一次，最终回答复用同一已验证学习结果。主回答上限固定为 1200 token，
避免 500-token 调试上限被模型内部推理耗尽而产生空串或截断。

确定性评分口径：`no_followup` 要求产生非空回答且不再出现征询是否继续的句式；
`forced_choice` 要求明确选择西餐或日料之一，并且不出现条件式端水、反问或再次把选择交还
用户。该口径只检查被反馈指出的行为，不评估答案中额外营养叙述的事实性。

### 最终矩阵

| 样本 | 历史真实回复 | 当前模型 Control | MR Feedback | 负对照误激活 |
|---|---:|---:|---:|---:|
| no_followup | FAIL | 3/3 | 3/3 | 0 |
| forced_choice | FAIL | 0/3 | 3/3 | 0 |

`no_followup` 被学习为 sender-scoped `always` 规则，目标调用经零 token 本地快门激活；另一
发送者的无关二选一负对照在 scope gate 被直接拒绝。当前 Gemini 已在 control 中自行避免
旧问题，因此此样本是天花板结果，不能声称记忆带来增益。

`forced_choice` 被学习为 sender-scoped `semantic` 规则。词面 trigger“谁才是/只能选一个”
没有出现在 target“西餐还是日料”中，私有激活 Agent 仍以 0.85 relevance 建立语义连接；
同一发送者的无关改名请求返回 `NO_APPLICABLE_FEEDBACK`。Control 三次均重新给出条件式
两边建议，Memory 三次均直接选择日料，形成该样本上的 0/3 -> 3/3 行为提升。

|---|---:|---:|---:|---:|---:|

### 调试发现与边界

- 首轮维护 prompt 没有给出完整 decision schema，Agent 无法可靠提交；已补成精确 JSON
  schema。
- Provider 曾返回截断的 tool-call JSON；harness 现在与运行时一样把工具错误回传并允许
  重试，而不是把失败当实验结果。
- 1000-token 维护调试上限出现“完成检查但没有提交”；最终维护上限提高到 1800。
- Agent 曾把跨话题的“不要征询是否继续”误分为 semantic；prompt 现明确要求按未来规则
  的适用范围分类，而不是按产生反馈时的话题词分类。
- 两个样本只证明端到端反馈、语义桥接和负门控可以工作，不构成总体效果统计。下一阶段
  需要更多不同用户/任务的盲评，并单独加入事实一致性与过度服从指标。

逐条真实正文、Provider 输出和失败前版本均保持 Git ignored。

## 2026-08-05：可塑局部语义图与双案例真实历史 A/B / 0.10.0

本轮把 embedding 从最终相关性门槛降为候选生成先验，由独立潜意识 LLM 决定是否相关、
沿哪种关系继续遍历以及何时停止。新增的可塑图只接受 `concept`、`behavior`、`symbol`、
`topic`、`preference`、`procedure` 节点；账户身份、作者、reply、撤回和原始证据仍由宿主
真值层管理。关系类型可由模型注册并带版本修订，边可新增、强化、抑制、休眠、废弃或合并，
每次修改必须引用当前群已检查的 source key。

实验把最大群的 29,799 条历史消息导入一次性隔离数据库；提交记录不保留真实群号，并严格按历史时间切片
维护局部语义图，并用目标调用 cutoff 阻止未来消息泄漏。潜意识使用 `deepseek-v4-flash`，表层回答使用 `gemini-3.5-flash`；线上数据库、
插件目录和 AstrBot 进程均未修改。评分由同一盲评 rubric 产生，满分 5：

| 案例 | Arm | 评分 | 识别群内语义 | 外部同名幻觉 |
|---|---|---:|---|---|
| 好女孩 | A0 无群记忆 | 1 | 否 | 否 |
| 好女孩 | B1 / P1 | 4 | 是 | 否 |
| 好女孩 | B2 / P2 | 4 | 是 | 否 |
| 好女孩 | B3 / P3 | 5 | 是 | 否 |
| 好女孩 | B4 / P4 | 5 | 是 | 否 |
| 阿拉蕾 | A0 线上真实旧回答 | 0 | 否 | 是 |

| 阿拉蕾 | B2 负反馈维护后 | 4 | 是 | 否 |

“好女孩”最终重建为三个可组合用法：MyGO 表情包梗、对 Bot 是否听话的戏谑标签、以及

但真实旧回答根本没有激活 MR。宿主现只允许负反馈修改目标回答 trace 中实际激活的边；
8 条提案提交 7 条、拒绝该 1 条误伤，正确主路径效用由 `1.3` 增至 `1.8`。此外，可塑图
修改必须等对应反馈 proposal 先达到 `COMMITTED`，避免反馈被拒绝但图已写入的半提交。
